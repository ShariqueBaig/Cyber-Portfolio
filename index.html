WB-01 · The Watch Bazar Critical

Hardcoded Supabase credentials in the client bundle

The production Supabase URL and anon key sit inside the JavaScript bundle. With the key, anyone can query the database REST endpoints directly and skip the backend entirely.

  1. Open DevTools, then Sources, then the main bundle.
  2. Search for supabase.co to find the initialisation string and key.
RemediationSupabase · SQL
- anon key can read any table + alter table orders enable row level security; + create policy owner_read on orders + for select using (auth.uid() = user_id); -- deny by default, then allow per role

WB-15 · The Watch Bazar High

Seller financial data exposed to every other seller

The Product API returns commissions and net profit to any authenticated seller, whoever owns the listing. A competitor can scrape every store's margins.

  1. Authenticate as Seller A.
  2. Request Seller B's product ID and read pricing_breakdown in the JSON.
RemediationDjango · Python
- fields = [..., "pricing_breakdown"] + def to_representation(self, product): + data = super().to_representation(product) + if self.context["request"].user != product.store.owner: + data.pop("pricing_breakdown", None) + return data

Finding 09 · University portal Critical

Password reset code can be sent to any email address

The reset request takes the destination email from the client request body. Change it and the one-time code goes to the attacker, who can then set the victim's password.

  1. Start Forgot Password for a target ID and intercept the OTP request.
  2. Replace the email field with an attacker address and use the code received.
RemediationNode · Express
- sendOtp(req.body.email) + const { email } = await getUser(session.userId) + sendOtp(email) // never accept a delivery address from the client

WB-11 · The Watch Bazar Medium

Duplicate orders by changing one character of the key

Checkout checks the Idempotency-Key header but never validates the payload against it, so a new key places the same order again.

  1. Record the key from a checkout and replay it: rejected.
  2. Change one character of the key and resend: a new order is created.
RemediationDjango · Python
- if Order.objects.filter(idempotency_key=key).exists(): + digest = sha256(canonical_json(body)).hexdigest() + if Order.objects.filter(body_hash=digest, + created__gte=window).exists(): + return duplicate_response()

The blind spot

Hire only a tester and you get a diagnosis, not a cure.

  • Missed

    A 16-finding PDF, and nobody on your team who can write the row-level security policy that closes the first one.

  • Missed

    Fix advice like “enable RLS” with no code. A policy that is slightly wrong still leaks, or locks real customers out.

  • Missed

    No retest by someone who knows both the exploit and the patch, so fixes ship unproven.

How an engagement runs

Methodology-driven, with evidence at every step. Testing ends with a report; for build and fix work it continues into the code.

  1. Reconnaissance

    Passive and active recon to map the attack surface: technology fingerprinting, subdomain enumeration, API endpoint discovery, client-side source analysis.

  2. Vulnerability discovery

    Automated scanning (Burp Suite, ZAP, ffuf) combined with manual testing against OWASP WSTG and the Top 10 across the whole stack.

  3. Exploitation and proof of concept

    Safe, controlled exploitation with evidence: requests, responses, screenshots and reproducible steps. Nothing destructive.

  4. Business logic testing

    Payment flows, privilege escalation, authentication bypass and workflow manipulation, the things scanners miss.

  5. Report and remediate

    Executive summary, CVSS-scored findings, reproduction steps and prioritised fixes. For build and fix engagements I write the patch as well.

  6. Verify and retest

    I rerun the exploit after the fix to confirm it holds, then stay on for ongoing assurance if you want it.
