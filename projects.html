Critical

WB-01 · Hardcoded Supabase credentials in the client bundle

The production Supabase URL and anon key sit inside the Vite JavaScript bundle. With the key, anyone can query the PostgreSQL REST endpoints directly and bypass the Django backend. Fix: move database access server-side, or enforce strict Row Level Security on every table.

High

WB-13 · No row-level security on SELECT for several tables

Unauthenticated users could dump tables such as brands through the REST API, and storage assets still pointed at an older staging project. Fix: enable RLS on all tables and migrate assets to the production project.

High

WB-15 · IDOR exposing seller financial data

The Product API returned commissions and net profit (pricing_breakdown) to any authenticated seller, whoever owned the listing. Fix: a serializer that includes the field only for the listing owner.

High

WB-10 · Broken account creation (authentication DoS)

When the confirmation email failed, the backend rolled back the new account, which blocked every new sign-up. Fix: repair the email provider config and handle the failure without deleting the account.

High

WB-04 · Client-side rate limiting, trivially bypassed

Login throttling lived in localStorage; removing one key reset it. Fix: server-side rate limiting on the Django backend.

High

WB-02 and WB-05 · API route map and admin endpoints disclosed

The JavaScript bundle listed every /api/v1/ route, the full role hierarchy and the admin endpoints, handing an attacker the map for IDOR and privilege-escalation testing. Fix: code-split admin routes and enforce server-side authorization on all of them.

Medium

WB-14 · IDOR on order tracking

Any authenticated seller could view the status and store ownership of any order by changing the order number. Fix: check that the requester owns the order or its store.

Medium

WB-11 · Weak idempotency on checkout

Replaying a request was rejected, but changing one character of the Idempotency-Key created a duplicate order, because the payload was never hashed. Fix: store a hash of the canonical request body alongside the key.

Medium

WB-06 · Session token storage key disclosed

The localStorage key holding auth tokens was visible in client code, making token theft simple if XSS is found. Fix: HttpOnly cookies.

Low / Info

Six lower-severity and positive observations

Public DRF browsable login (WB-12), client fingerprint header (WB-07), file-type validation gap on uploads (WB-16) and ghost 200 responses (WB-09). Also recorded as good practice: the OAuth flow had moved to PKCE (WB-03, fixed) and robots.txt was hardened (WB-08).

Critical

SQL Injection in the Login Endpoint

The login endpoint concatenates the ID parameter into a SQL query. A single quote breaks the query and a trailing comment restores it, confirming injection. A WAF blocked automated extraction, but the unparameterized query is still the root cause. Fix: prepared statements and numeric-only ID validation.

Critical

2FA Bypass: Client-Side Email Manipulation

Two-factor authentication OTP sent to email address from client request body instead of server session. Attacker can redirect OTP to their own email for full account takeover.

Critical

2FA Completely Non-Functional

Session upgraded to "fully authenticated" immediately after first-factor login. Any arbitrary code accepted. Direct URL navigation bypasses 2FA entirely, providing zero security value.

Critical

Account Takeover via Password Reset

Password reset OTP can be redirected to attacker-controlled email by modifying the request body. Total account takeover of any user.

Critical

Inconsistent SSL/TLS Enforcement

Password reset functionality downgrades to plaintext HTTP. Credentials transmitted in cleartext, enabling network-based interception.

High

Privilege Escalation via Parameter Pollution

Appending ?role=admin to API requests returns admin-level data. URL params override session data, exposing administrative functionality to low-privilege users.

High

Unchanged Passwords Post-Compromise

After a previous security incident, all user passwords remained unchanged for 3+ months. Any stolen credentials from the prior attack remain valid.

Medium

Unsanitized SVG File Upload in Avatar Feature

Discovered that the platform's avatar upload accepted SVG files without sanitizing their contents. SVG files can embed JavaScript and HTML, enabling potential Stored XSS. While the impact was limited in this case (avatars weren't publicly displayed to other users), the lack of server-side validation represented a significant security gap.
